# GymOS Security Specification

## 1. Core Data Invariants
1. **Strict Tenant Isolation**: Every gym-owned record (`/gyms/{gymId}/members/*`, `/gyms/{gymId}/memberships/*`, `/gyms/{gymId}/member_payments/*`, `/gyms/{gymId}/payment_receipts/*`, `/gyms/{gymId}/attendance/*`, `/gyms/{gymId}/staff/*`, `/gyms/{gymId}/membership_plans/*`, `/gyms/{gymId}/notification_logs/*`, `/gyms/{gymId}/notifications/*`, `/gyms/{gymId}/settings/*`) belongs strictly to `gymId`. Users belonging to Gym A can never read, list, create, update, or delete records in Gym B.
2. **Account Suspension & Subscription Expiry Lock**: If `gyms/{gymId}.accountStatus == 'SUSPENDED'`, `gyms/{gymId}.subscriptionStatus` is not `'TRIAL'` or `'ACTIVE'`, or `gyms/{gymId}.subscriptionAccessUntil <= request.time`, all operational reads and writes under `/gyms/{gymId}/*` are denied at the database rule layer for non-Super-Admin users while preserving all tenant data.
3. **Controlled Super Admin Governance**: No hardcoded bootstrap email exists in code or rules. Only existing admins registered in `/platform_admins/{uid}` or a controlled server-side bootstrap (`SUPER_ADMIN_BOOTSTRAP_TOKEN` / CLI script when `platform_admins` is empty) can grant `SUPER_ADMIN`. Regular users and gym owners cannot promote themselves to `SUPER_ADMIN` or alter platform settings, subscription plans, or gym subscription status.
4. **Database-Enforced Public Registration Gate**: `platform_settings/default.allowPublicRegistration` is enforced directly inside `firestore.rules` on self-service `gyms` and `users` creation. When `false`, only Super Admin gym creation + `GYM_OWNER` / staff invitations can onboard new accounts.
5. **Granular Staff Permission Enforcement**: Staff deactivation immediately revokes access across `/users/{uid}` and `/gyms/{gymId}/staff/{uid}`. Trainers (`GYM_TRAINER`) and receptionists without explicit payment permissions (`canViewPayments`, `canRecordPayments`, `canConfirmPayments`) are blocked at the Firestore rules level from reading financial ledgers or confirming payments.
6. **Manual Payment & Receipt Integrity**: Member payments require confirmation authority (`canConfirmPayments`) to reach `CONFIRMED`, prevent duplicate confirmation or amount tampering, and issue immutable receipts.
7. **Immutable Audit Trail**: `audit_logs` records require `actorUid == request.auth.uid`, matching tenant `gymId` membership when `gymId` is present, and `createdAt == request.time`, and can never be updated or deleted.
8. **PII Protection & Bounds**: All IDs match `^[a-zA-Z0-9_\-]+$`, strings have explicit `.size()` bounds, schemas use `hasAll` + `hasOnly`, and updates use `affectedKeys().hasOnly(...)`.
